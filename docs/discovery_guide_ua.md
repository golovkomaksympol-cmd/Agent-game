# Discovery: питання до клієнта

**До концепту:** [Agent Attention Game v0.2](agent_attention_game_concept_ua.md)  
Версія: 0.1 · 12 жовтня 2026 року

## Мета розмови

1. Зрозуміти, **яка саме проблема** болить: шум від окремого агента (поріг ескалації) чи конкуренція багатьох агентів за увагу людини.
2. Зібрати параметри, без яких механіку неможливо налаштувати: права на рішення, критичні тригери, ваги проєктів, доступність людини.
3. Домовитися про дані й критерії успіху для пілота.

Питання з позначкою ★ — обов'язкові для першої розмови (≈ 60 хв). Решту можна закрити асинхронно.

## Пропонований порядок (60 хв)

| Хв | Блок |
|---|---|
| 0–5 | Мета, формат, що ми вже знаємо |
| 5–20 | A. Поточний біль і масштаб |
| 20–35 | B. Права на рішення та ризики |
| 35–45 | C. Людина: доступність і вподобання |
| 45–55 | D–E. Агенти, пріоритети, критерії успіху |
| 55–60 | Наступні кроки й запит даних |

## A. Поточний біль і масштаб

| # | Питання | Навіщо / яке рішення від цього залежить |
|---|---|---|
| A1 ★ | Скільки зараз агентів і проєктів? Скільки людей отримує від них запити? | Чи взагалі є конкуренція за увагу; одна людина чи кілька ролей |
| A2 ★ | Розкажіть про 2–3 останні випадки, коли агент «задовбав». Що саме він питав, коли, через який канал? | Конкретика замість загального враження; перші приклади для розмітки a/b/c/d |
| A3 ★ | Це один агент чи сумарний шум від багатьох? | Один → поріг ескалації (P1). Багато → координація (P2–P3) |
| A4 | Скільки звернень на день зараз і скільки з них ви вважаєте зайвими? Приблизно. | Базова лінія та ціль |
| A5 | Чи були випадки, коли агент **не** спитав, а мав? Що сталося? | Ризик протилежної помилки; калібрування Правила 0 |
| A6 | Чи траплялося, що важливий запит загубився серед дрібних? | Чи справді потрібна пріоритизація |
| A7 | Що ви робите зараз зі зайвими запитами: ігноруєте, відкладаєте, відповідаєте коротко? | Поточні «обхідні шляхи» людини; revealed preference |

## B. Права на рішення та ризики

| # | Питання | Навіщо |
|---|---|---|
| B1 ★ | Які дії агент **завжди** має погоджувати з вами, незалежно від будь-яких обмежень? | Клас `must-ask` |
| B2 ★ | Які рішення агент може ухвалювати сам, якщо потім повідомить? А які — навіть не повідомляючи? | Класи `may-ask` / `must-not-ask`, FYI-журнал |
| B3 ★ | Які пороги важливі: сума грошей, зовнішня комунікація, незворотність, персональні дані, юридичні питання? | Числові пороги для Правила 0 |
| B4 ★ | Що для вас «справді критично, турбувати негайно»? Дайте 3–5 прикладів. | Закритий список критичних тригерів |
| B5 | Хто ще, крім вас, може ухвалити рішення, якщо ви недоступні? | Делегування, режим деградації |
| B6 | Чи прийнятно, щоб агент діяв за запасним варіантом, якщо ви не відповіли до дедлайну? Для яких дій — ні? | Межі `fallback_action` |
| B7 | Як ви ставитеся до того, щоб система зрідка підкладала контрольний запит із навмисною вадою для перевірки якості нагляду? | Чи можна міряти «автоматичне схвалення» |

## C. Людина: доступність і вподобання

| # | Питання | Навіщо |
|---|---|---|
| C1 ★ | Коли вам зручно приймати складні рішення, а коли — лише швидкі «так/ні»? | Типи слотів `deep` / `quick` / `digest` |
| C2 ★ | Що краще: кілька пакетів на день у фіксований час чи один дайджест? Скільки разів на день максимум? | Кількість слотів, `C_switch` |
| C3 | Через який канал вам зручно отримувати запити? Чи є канал, який не можна використовувати? | Інтеграція доставки |
| C4 | Чи хочете ви бачити повну чергу запитів, чи лише те, що система вирішила показати? | Правило 9, Pull-режим |
| C5 | Чи можна читати ваш календар (лише зайнято/вільно)? | Обмеження календаря; приватність |
| C6 | Скільки часу на день ви готові віддавати агентським рішенням? | Стартовий глобальний ліміт |
| C7 | Чи готові ви коротко оцінювати складність рішень, наприклад раз на день? | Калібрування SP без додаткового шуму |

## D. Агенти й технічна сторона

| # | Питання | Навіщо |
|---|---|---|
| D1 ★ | Як побудовані агенти: на якій платформі, хто їх підтримує, чи можемо ми змінювати їхні інструкції? | Чи реалістичні P1 (правила в промпті) і поле `InteractionRequest` |
| D2 ★ | Чи логуються звернення агентів зараз? Чи можемо отримати вивантаження за 2–4 тижні? | Етап 0, офлайн-прогін |
| D3 | Що агент робить зараз, поки чекає відповіді? | Blocked time, Правило 10 |
| D4 | Чи бачать агенти один одного, чи є спільні ресурси або залежності між проєктами? | Чи потрібна координація поверх черги |
| D5 | Хто відповідатиме за supervisor і правила після пілота? | Власник процесу, підтримка |

## E. Пріоритети, цінність і критерії успіху

| # | Питання | Навіщо |
|---|---|---|
| E1 ★ | Як ви ранжуєте проєкти за важливістю? Хто це вирішує і як часто змінюється? | Ваги проєктів, квоти |
| E2 ★ | Як через 6–8 тижнів ви зрозумієте, що стало краще? Що буде успіхом у цифрах? | Критерії успіху та зупинки |
| E3 | Як порівнювати цінність рішень у різних проєктах, якщо KPI різні? Чи достатньо шкали «немає / низька / середня / висока ціна затримки»? | `cost_of_delay`, несумірні KPI |
| E4 | Чи є проєкти, які можуть отримувати менше уваги без шкоди? А ті, що не можуть чекати взагалі? | Гарантія від голодування, резерв |
| E5 | Що для вас неприйнятний результат пілота? | Червоні лінії |
| E6 | Хто може розмітити 50–100 історичних запитів (≈ 1–2 год)? | Головний датасет для старту |

## Запит даних після розмови

- [ ] Вивантаження звернень агентів за 2–4 тижні: час, агент, канал, текст, час відповіді, реакція.
- [ ] Список проєктів і їхні ваги.
- [ ] Чернетка правил: `must-ask`, пороги, критичні тригери.
- [ ] Типовий тиждень календаря (лише зайнято/вільно) або опис доступності.
- [ ] Контакт людини, яка розмітить історичні запити.

## Сигнали, що ігрова механіка (P3) не потрібна

- Шум переважно від одного агента або класу «a» (мав вирішити сам).
- Агентів мало (≤ 3) і їхні запити рідко збігаються в часі.
- Людина готова до фіксованого дайджесту й не потребує тонкого розподілу.

## Сигнали, що P2–P3 варто розглядати

- 5+ агентів, які одночасно претендують на одну людину.
- Є важливі запити, що губляться серед дрібних.
- Малі проєкти систематично чекають тижнями.
